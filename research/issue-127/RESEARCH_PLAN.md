# Issue #127 — live Text-Fabric GitHub-backend verification

## Research checkpoint

### Failure observed

The first `v0.2.0` publisher run (`34471072469`) successfully completed preflight, full pinned-corpus asset construction, draft publication, draft-byte revalidation, and promotion. The public-release validation step in `verify-live` also downloaded the four public assets and passed `validate_distribution`.

The next step, `Fresh-cache tagged load then network-blocked local reload`, failed before Text-Fabric could acquire the release:

```text
Backend provider github not supported.
Cannot reach online data on github
Try installing text-fabric one of the following:
pip install text-fabric[github]
pip install text-fabric[all]
...
fresh tagged Text-Fabric load failed
```

Failing job: `102851819728` in workflow run `34471072469`.

### Exact release/workflow state

The release candidate and immutable project identity remain:

- release tag: `v0.2.0`;
- release commit: `317e960e05ca7f36f35a11fcf567285312951095`;
- package/materializer version: `0.2.0`;
- Text-Fabric data version: `0.2`;
- pinned OCP commit: `c939dcbacad78c5d18d2c4282cad23c47e19ac07`.

At the release commit, `.github/workflows/publish-corpus-release.yml` installs the package in `verify-live` with:

```bash
python -m pip install .
```

and later calls `tf.app.use(... checkout=release_tag)` against GitHub.

The project dependency surface in `pyproject.toml` intentionally uses base Text-Fabric (`text-fabric>=13.1,<14`) rather than a provider-specific extra.

### Upstream Text-Fabric dependency contract

Text-Fabric's upstream packaging at commit `0c45c386916cb52be84098796ec27ce97e5bf9fc` declares GitHub transport as an optional extra:

```ini
[options.extras_require]
github = pygithub>=1.57
```

The live failure message is generated by Text-Fabric itself and recommends installing `text-fabric[github]` (or `[all]`). Therefore the missing dependency belongs to the GitHub-backed verifier environment, not to corpus semantics or the base converter runtime.

### Ownership conclusion

Do not add PyGithub or `text-fabric[github]` to Pseudepigrapha-TF's ordinary runtime dependencies solely to make release CI reach GitHub. That would broaden every installation for a capability only the network-backed verifier requires.

Provision the optional GitHub backend explicitly in the live verification environment, constrained to the same supported Text-Fabric range (`>=13.1,<14`).

### Release-integrity conclusion

The published `v0.2.0` corpus generation is not shown corrupt by this failure. Before the failing `tf.app.use` call, the public four-asset set was downloaded and passed exact distribution validation. The tag currently dereferences to the approved release commit.

The fix must not move/recreate `v0.2.0`, replace its assets, or rerun the destructive publisher against the existing release. Corrected evidence must come from a read-only verification path against the already published generation.

## Implementation plan

1. Add a workflow-contract regression that requires GitHub-backend provisioning in the live verification environment before GitHub-backed `tf.app.use` is exercised.
2. Keep a regression proving the normal project dependency remains base `text-fabric>=13.1,<14` and does not absorb PyGithub/provider extras.
3. Change `publish-corpus-release.yml` minimally so future `verify-live` jobs install `text-fabric[github]>=13.1,<14` after installing the exact release package.
4. Add a reusable/read-only published-release verification workflow rather than rerunning the destructive publisher. It must accept/freeze a tag and expected commit, resolve the tag to that commit, download and validate the existing public asset set, perform a fresh tagged Text-Fabric acquisition, then prove `checkout='local'` reload with network access blocked. Give it read-only repository permissions.
5. Add contract tests proving the read-only verifier has no release mutation path and preserves both fresh-cache and offline-reload checks.
6. Demonstrate RED before production-workflow changes through branch CI.
7. Implement the minimal fix, run canonical CI, and perform an exact-head logically independent adversarial review.
8. Merge only if review and CI are green.
9. Execute the read-only verifier against `v0.2.0` / `317e960e05ca7f36f35a11fcf567285312951095` without changing release bytes.
10. Re-read tag dereference and the four public asset digests after verification. Record evidence in #127/#104, then proceed to the Agora pin update.

## Review threats to test explicitly

- The verifier-only dependency accidentally leaks into normal package requirements.
- The extra is unconstrained and upgrades Text-Fabric beyond `<14`.
- A verification workflow contains `contents: write`, `gh release create/edit/upload/delete`, tag mutation, or another destructive path.
- The verifier trusts `target_commitish` instead of dereferencing the actual tag object/ref.
- The fresh load succeeds but the supposed offline reload still has network access.
- A future publisher edit regresses to base-only installation before its GitHub-backed live check.
- Corrective verification silently republishes or replaces the already validated `v0.2.0` assets.
